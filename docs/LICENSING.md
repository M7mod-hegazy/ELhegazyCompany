# POS Licensing — how it works & the recommended setup

## What already exists (in `D:\code\retailer`)

The POS app ships with a complete **offline** licensing system:

- Every install computes a **machine code** (hardware fingerprint, 32-hex chars, shown with a QR
  on the activation screen).
- A license is an **Ed25519-signed token** (`RTL2.…`) bound to that machine code. The app verifies
  it locally with an embedded **public key** (`retailer/shared/licensing/publicKey.js`) — no
  internet needed, ever.
- The matching **private key** is the seller's secret. It was generated by
  `retailer/tools/license-signer/keygen.js` and lives OUTSIDE the repo on your PC.
- There is also a standalone `retailer/vendor-license-service/` (Express + SQLite) with
  online-activation endpoints — **you do not need to run it** (see recommendation).

## Recommendation (what this site now implements)

**Make the website the vendor console.** Best practice for your scale:

1. **Keep the offline token flow** — it's already built into the shipped app, works without
   internet (a real selling point), and can't go down.
2. **Issue licenses from this site's admin** (`/admin/licenses`): paste the customer's machine
   code → the site signs an activation token with the same private key → you send it via WhatsApp.
   Every license is recorded in MongoDB (customer, phone, order ref, expiry, token) so you have
   live central control and history.
3. **Subscription-style control when you want it**: issue tokens with an expiry date (e.g. yearly).
   The app enforces expiry offline (with a clock-rollback guard). Renewals = issue a new token from
   the same screen.
4. **Skip the separate vendor-license-service** unless you later need automatic online activation
   at volume. Its committed default keys must be treated as compromised; the site's flow replaces
   it with less moving parts.

## Setup (one time)

1. Find the private key produced by keygen (outside the retailer repo — keygen printed its path;
   it is a `-----BEGIN PRIVATE KEY-----` PKCS8 PEM). Its public half must equal the one embedded
   in `retailer/shared/licensing/publicKey.js` for shipped builds to accept your tokens.
2. Set these environment variables (locally in `.env.local`, and in Vercel → Settings →
   Environment Variables):

   ```env
   LICENSE_PRIVATE_KEY_PEM="-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----"
   ADMIN_PASSWORD=<a long random password for /admin>
   MONGODB_URI=<your Atlas connection string>
   ```

   (The PEM can be pasted with `\n` escapes or base64-encoded — both are accepted.)
3. Done. `/admin/licenses` can now mint activation codes identical to the ones
   `tools/license-signer` produces.

## Selling flow end-to-end

1. Customer orders the full version on the site (`/order?product=pos&plan=full`) → order saved
   with a reference (e.g. `HGZ-4K7TQ9`) → customer lands on WhatsApp with that reference.
2. You confirm payment (Instapay / Vodafone Cash / transfer), send the full installer.
3. Customer opens the app → activation screen → sends you the **machine code** (text or QR photo).
4. You open `/admin/licenses` → New license → paste machine code, customer name, expiry (or
   perpetual) → copy the generated activation code → send it on WhatsApp.
5. Customer pastes it in the app → activated, offline, bound to that PC. Rebinds (new PC) = issue
   a new token; suspends = let the expiry lapse or issue a short-dated token on renewal plans.
